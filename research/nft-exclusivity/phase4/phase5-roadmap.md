# Phase 5 implementation gates

1. **Obtain the economic acceptance contract.** Pin the release's source mapping and ask the native protocol owner to specify balance and credit reservation identity, every alternative debit, reclaim, duplicate collection, recovery and migration exit, rules after divergence, and beneficiary redemption. Require source or independently testable evidence with a named trust root. If liabilities can be revised by governance, define who bears the loss and the scope of finality.
2. **Choose the smallest enforceable fence.** If a native exclusive reservation exists, prove conflict coverage and make its evidence portable. Otherwise require the native authority to partition funded capacity into irrevocable per-sale rights or coordinate all incompatible account debits at the source. A terminal committee that only sees RAVEs cannot close a native bypass. Define fees, credit changes, multiple units, partial fills and migration before admitting such a profile.
3. **Make preparation bilateral.** Agree on a pre-reservation sale-intent digest and unique nonce. Certify the NFT grant against that intent. Reserve capacity only for that grant, then require the terminal statement to bind the actual parked action and prepared title. Prove no digest cycle, no early discretionary debit and a safe failure path if reservation never completes. Locking the NFT until buyer consent may be indefinite and needs explicit acceptance.
4. **Implement versioned integrity checks.** Use the existing Phase 3 validated-read pattern and shared native/WASM verifier behind fixed per-network public roots. Exercise Paid, Void, insufficient evidence, exact replays, independently obtained signed dependencies and cross-epoch refusal. Keep grant execution distinct from fresh title attestation. Verify new code against pinned Holochain and release versions before deployment.
5. **Require recoverable completion.** Between independent hosts, test crash points before assembly and before archive acknowledgment. Establish replication or threshold reconstruction of all dependencies and keys' antirollback boundaries. Measure retrieval under latency and participant loss. Give clients separate indicators for irrevocable entitlement, complete proof delivery and collected funds.
6. **Coordinate import cutover.** Obtain an exclusive source export shared by all CEL importers, settle previously issued legacy receipts, and define the economic status of old client versions. A destination registry alone leaves native circulation possible.
7. **Reopen funded acceptance only after evidence.** In disposable production-equivalent deployments, verify both outcomes and onward transfer against authenticated source proofs from independent observers. Include governed recovery, evolution of spending limits, isolated partitions and old-epoch exits in the acceptance specification. Keep research units until finality scope and production policy are explicit.

## Repository reuse

The existing [pinned component inventory](../phase3/cross-repository-inventory.md) provides source paths and versions. Phase 4 directly reused the Phase 2 receipt library, Phase 3 native verifier and guarded baseline, hNFT mint zomes and adapted agreement script. The DEX history-walk reclaim design supplies the abstract competing-exit case; its mock currency cannot validate a native payment. Authenticated-state record-status checks and certified frontiers apply to historical dependencies; unique current state still needs a decision authority. FROST could reduce signature bytes at the cost of additional rounds, share/nonce persistence and reduced signer attribution. It would leave source conflict coverage unchanged. Verifiable time is suitable for proposal eligibility. Verified admission can bind committee eligibility but does not prove operator independence. The agreement UI can expose execution, collection, proof availability and economic finality as separate states. These supporting repositories were assessed for compatibility using pinned Phase 3 findings. Their full suites and any later private branch changes were not revalidated in Phase 4.
