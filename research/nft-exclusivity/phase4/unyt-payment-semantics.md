# What the funded fixture establishes

The stock Sandbox v0.117.0 distributes the Alliance integrity and coordinator WASMs, an hApp and an operational CLI. We installed the release on Holochain 0.7.1, then repacked the **same WASMs** with a private network seed and a freshly generated progenitor in the DNA properties. Two separately keyed cells used a memory transport on one conductor. Official CLI setup granted the founder 100 units of special credit. The founder committed 10 to the buyer, who accepted and used the resulting balance. The payment issuer in this path is the release application. Its credit policy, operators, identities and economic unit are local fixtures. No external network honored these units. [Official release](https://github.com/unytco/unyt-sandbox/releases/tag/v0.117.0) · [Execution capture](results/settlement.jsonl)

| Interface | Independently supportable statement | Boundary |
|---|---|---|
| Chain actions and ledger | The conductor authenticates author actions. The public engine's Ledger::on_chain and carried_by reconstruct balances along a selected ancestry, including committed and parked amounts and carried state. An admitted credit rule permits additional spending. | Branch-relative history, potential revision and visibility. A CLI JSON export itself carries no verified action signature. Externally supplied credit policy matters. |
| Parked spend | The spend records the agreement, role, executor and amount. The engine derives the role's allocation input from its parked data. Parked balance and parked credit affect separate buckets. | A native reservation was observed. Universally exclusive reservation of the underlying balance or credit capacity was not established. |
| Agreement and execution | Code template, agreement instance, global definition, role admission and execution inputs determine allocation. The release produced the exact agreed seller, unit, quantity and parked source. The public interpreter exposes typed RAVE inputs/outputs and history functions. | Deterministic calculation is conditional on authenticated inputs and their selected histories. The release's embedded interpreter version was not independently mapped to source. |
| Seller receipt | Seller collected from the RAVE. Its visible ledger increased by exactly 10 units. The buyer's cell retrieved the execution. | Historically applied credit. Offline verification of the capture does not establish current solvency, unrevoked backing or exclusion. |
| Rejection and reclaim | ReclaimInput references a rejection. The public negative-history ledger code distinguishes proposed and committed value. An accepted history and a rejection have different rules. Fees can survive reversal. | This is not a general rule permitting a timeout refund of a parked spend. Require the precise exit and its validation contract for each instrument. |
| Locked/carryover and recovery | Lockbox code and successive execution state can constrain distributions. System unit recovery checks the supplied activity for whether an item was answered, uses assigned recovery roles and carries the recovered set forward. | Branch-dependent reads and privileged recovery rules. Neither a locked flag nor a recovery agent proves source exclusivity. |
| Migration | Notary service signs a closure statement after verification of the agent-chain close operation. A close/summary and a qualifying history can be consulted by the agreement engine. | A valid close observed on one ancestry is historical evidence. Cross-epoch conservation requires a unique export and permanent fencing of the old authority. |
| Warrant, standing and validation | Local integration status and returned records identify what a node accepted or currently sees. A discovered divergence can supply accountability evidence. | No independently authenticated assertion of complete network visibility, guaranteed detection time, or exhaustive economic disposition was established. A warrant's consequences for already collected or migrated credit need a versioned recognition contract. |

The hNFT template at 8fd2391 used buyer_spends. The stock release rejected this input at parking. The experimental adapter changes that input throughout the script and schemas to buyer_spender_allocations, fixes the seller, NFT and buyer admission, and creates a new template and agreement. Its executable script SHA-256 is recorded in each signed grant. This is an intentionally different agreement identity. The application itself does not check the CEL grant before spending. The experiment orders grant certification before execution in the driver. Using this template with arbitrary callers as a two-sided exchange would leave the buyer exposed. [hNFT source](https://github.com/ConorTttttt/hNFT/tree/8fd2391e2f9f584c19dcb329bb21bc034f1bf19e/unyt/nft_sale_settlement) · [Original rejection](results/funding.jsonl)

The 0.7.1 release's create_parked_spend returned a **CreateLink action** in the funded experiment. Its signed base identifies the Smart Agreement and its tag carries the role and amounts. Using that link hash as the funded asset's globally unique identity would be a category error. More than one action could name spending decisions about the same account capacity unless an authoritative rule excludes that possibility. The RAVE and ordinary seller collection were Create actions carrying distinct app entries.

The structured native records can also be exported including signatures. In the subsequent run, the buyer retrieved five through hdk_must_get_valid_record. Their signatures, action identifiers, entry hashes and application-level relationships were independently checked offline. This supports attribution of the historical funding and collection records beyond trusting the CLI JSON summary. It still leaves alternative histories and economic recognition unresolved.
