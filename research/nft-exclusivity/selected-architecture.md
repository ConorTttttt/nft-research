# Fixed-roster certification of independent rights

**Decision.** Give an ordinary NFT one title input. Create more genesis inputs only for enforceable rights with independently assignable controllers. Use the same certificate protocol for one transfer or an atomic bundle. Genesis supplies the entire rights namespace, initial controllers and an ordered roster of seven distinct keys. A deployment must bind human-facing right definitions to those IDs in its trust anchor. An issuer can still label two roots with the same artwork. The lab uses fixed roots in DNA properties and has no mint RPC.

1. The buyer obtains the parent proof and checks genesis, roster, lineage and what the entitlement covers. A presentation of an old certificate by itself only establishes history.
2. The controller constructs 1–256 moves sorted by unique 32-byte input ID. Each specifies one new controller. The canonical digest includes version/domain prefixes, the DNA-derived domain (including ordered witness keys), count, input IDs and raw recipient keys. The same controller signs the whole digest. Different owner and witness prefixes prevent cross-role substitution. There is no clock, sequence-number oracle or current-owner DHT query.
3. Each witness authenticates the inputs against verified genesis or cached outputs of verified histories. Within one SQLite immediate transaction it reserves each input for the statement digest. A mismatching reservation aborts the entire transaction. After durable commit it signs. Exact retries reissue a vote. A client can send to seven concurrently, collect five distinct votes and deliver the full proposal, signatures and dependencies to each buyer.
4. The verifier rejects malformed lists, duplicate indices, invalid owner or witness signatures, unknown parents, differing controllers, cross-domain data and weak keys. Each child ID hashes the statement digest and input ID under a distinct prefix. A child carries its ancestor's right and the designated controller. Deriving IDs from certificate bytes would let different five-of-seven subsets produce different spendable children.
5. The client can publish through the coordinator. An integrity zome replays a topologically ordered proof from DNA roots and checks signatures using the same pure Rust verifier. A batch is one statement. Anyone can relay it. DHT visibility, action authorship and receipt count have no effect on cryptographic finality. Application read paths must verify the bytes and require the expected right, recipient and DNA. The caller can trace individual right identity backwards through the explicit parent-child mapping.

**Holochain boundary.** Proof-carrying histories avoid asking validators whether a competing entry exists. In this prototype each submitted history is capped at 64 steps; a longer lineage can remain valid under the core yet cannot be published through this adapter. Full histories cost bandwidth and verification time. The upstream dependency API can instead defer validation on an unresolved named record. That does not certify absence. Source chains provide author attribution and asynchronous audit evidence. Native countersigning locks participants' local chains during a timed preflight. With a malicious owner and disjoint buyers it supplies no required honest common signer across the two sessions. The release gates countersigning behind a non-default feature. **Recovery.** Preserve the signed proposal and dependencies before sending. A witness that crashes after reservation and before sending can sign the same digest after restart. A buyer possessing a hidden certificate can relay it. Losing the only copies of a proposal or sufficient signatures can destroy availability. A timer, agent departure or lack of DHT results never authorises a replacement spend. Partitions can safely stall. There is no cancellation path. A malicious seller can lock its own assets by splitting votes. Production clients need durable outboxes and delivery acknowledgements.

**Membership and composition.** The prototype has one static roster per domain. An alternative handoff consumes the old tip under its existing roster and binds an approved new roster exclusively to the *child*. Competing handoffs then conflict under the old rules. This does not rescue an unavailable old quorum, guarantee honesty of the new roster, or protect history after later compromise of old keys. An administrator rebinding an existing input across epochs breaks safety. Transfers over independent rosters or controllers are unsupported. Partial certificates from separate transfers do not form an atomic sale. A real cross-domain protocol needs an agreed commit/abort outcome and recovery evidence for each participant.
