# Holochain is the proof publication boundary

The Phase 1 integrity zome replays a full, topologically ordered history from DNA-rooted genesis. The Phase 2 adapter instead carries the ancestry of **one entitlement**, up to 64 steps. Each step is a compact atomic transfer leaf or a signed reset proof. The genesis slot, initial controller, allowed recipients, roster, quorum and equivocation budget are pinned by the installed DNA and properties. Every signature binds a domain derived from the actual DNA hash, ordered keys and policy parameters. The numbers of atoms and steps are laboratory limits. A missing or longer history can block acceptance in this adapter even when a certificate is valid in the mathematical protocol.

The Rust integrity callback verifies Ed25519 signatures strictly, distinct indices, width and Merkle orientation, the current controller in that proof, membership of recipients, the reset inequality, and the deterministically derived next version. It validates create-entry and create-record operations and rejects updates to the application entry. The coordinator publishes a new History. Anyone may relay the proof. A delete or disappearance from a search result cannot revoke a cryptographic event. Normal Holochain chain authorisation still applies. The code handles fixed membership and the tree/reset formats; the flat format in the Python benchmark is a comparison control.

| Received evidence | Interpretation for an application |
|---|---|
| Owner proposal, subquorum votes, or a few closure reports | Pending. The coordinator exposes only a certified history format. Invalid or insufficient evidence fails integrity validation. |
| Certified history with an identified last step | Historical acquisition of the derived right by the resulting controller. Re-verify the expected genesis, recipient and terms before presenting purchase success. |
| An older valid history | Still authentic historical ownership. The current frontier may already have advanced. |
| Conclusive reset for a parent | All old transfers from that version excluded; controller retained at one fresh version. A revocation of an independent lease would require the corresponding policy guard. |
| DHT lookup or signed statement of “latest” | Discovery or provenance only. There is no linearizable current-owner endpoint. To buy, demand a final successor specifically authorising the buyer. |

The verifier uses the local DNA hash/properties and embedded evidence. It makes no DHT non-existence query and never locks a source chain to infer that another seller branch cannot exist. In upstream 0.7.1, must_get_valid_record names a record and can defer on unresolved dependencies or depend on visible authorities' validity reports. Countersigning preflight locks a local participating chain. Neither creates a common decision for disjoint buyer sessions with a malicious seller. Endpoint discovery can be replicated on the DHT; only an authenticated predecessor policy may designate which keys count. We compiled HDK 0.7.1 / HDI 0.8.1 with Rust 1.96.1 for wasm32-unknown-unknown. The stock 0.7.1 loopback conductor accepted proofs produced by independent Python signer processes using fresh keys. The HTTP bootstrap address used in this disposable test was loopback. Signers perform durable reservation outside Wasm. An actual service would require authenticated encrypted transport, durable client outboxes, protected signer provisioning, availability commitments and independent monitoring.
